# Decision log

Running log of non-obvious decisions, one entry each: what was chosen, what the alternative was, why. Appended as work happens, not written retroactively.

---

**No browser automation tool for the orientation walkthrough.** Alternative: skip the "log in as each role and click through" step entirely, or fake it. Chose instead to substitute source reading (every router read end to end) plus `curl`-driven tRPC calls against the real running dev server (login → cookie → protected query, on real seeded data) as the closest available equivalent, and to say so explicitly in `discovery-log.md` rather than imply a UI walkthrough happened. Why: the brief is explicit that AI use is judged on whether it's disclosed honestly, and every rule in scope for this refactor is server-side, so the substitute covers the behavior that matters even though it's weaker for pure UI concerns.

**Test DB strategy: temp SQLite file per test file, not `:memory:`.** Alternative: libSQL in-memory database. Chose a temp file (`DB_FILE` env var, per the seam the handover identified in `src/db/index.ts`) pushed with the real Drizzle schema before each run. Why: `@libsql/client`'s in-memory mode is a distinct code path from file mode and isn't what production uses; a temp file is closer to real behavior for negligible extra cost (SQLite temp-file I/O is fast), and matches exactly what `db:push` already does against `flexfit.db`, so the same push mechanism is reused rather than re-implemented for tests.

**`createCaller` over spinning up an HTTP server in tests.** Alternative: start the Next.js server and hit it with `fetch`/`supertest`. Chose `appRouter.createCaller({ db, user, token })` directly. Why: the handover already identified that `createContext()` calls `cookies()` from `next/headers`, which throws outside a real Next.js request — so an HTTP-level test would need to fake cookies/headers anyway. `ctx` is just `{ db, user, token }` and every router reads only `ctx.db`/`ctx.user`, so constructing that context object directly is both correct and far faster per test than booting a server.

**Time control via `vi.useFakeTimers({ now })` per test, not a single global freeze.** Alternative: freeze time once in a global setup file. Chose per-test `vi.setSystemTime`/fake timers scoped to each test (restored in `afterEach`). Why: the boundary conditions being tested (12h / 24h / 4h cutoffs) are relative to `new Date()` at call time, and different tests need different "now" values relative to a class's `startsAt` to hit exactly-at-boundary vs. just-inside vs. just-outside cases. A single global freeze would force all fixtures to be constructed relative to one fixed instant, which is more fragile than letting each test pick its own "now."

**Removed the dead `activeMembershipFor` copy from `reschedules.ts` during the `reschedule-rules.ts` extraction, rather than carrying it forward unused.** Alternative: leave the unused function in place untouched, to keep the extraction's diff to the strict minimum. Chose to delete it. Why: dead code has no runtime behavior — nothing calls it, so removing it cannot change any input/output/error/edge case, which is the actual constraint (not "minimize diff" for its own sake). Once `reschedule`'s and `validateReschedule`'s bodies were rewritten to call `evaluateReschedule`, the orphaned helper had no remaining reason to exist in that file and keeping it would read as an oversight, not a decision. The finding it was evidence for (`known-issues.md` #4 — reschedule never checks membership status) is unaffected and still proven by `test/reschedules.test.ts`'s bug #4 test, which passed unmodified before and after this extraction; `known-issues.md` was updated to describe the function in the past tense rather than cite line numbers that no longer exist.

**`evaluateReschedule` takes `(db, userId, input)` rather than the full tRPC `ctx`.** Alternative: pass `ctx` straight through, matching the router procedure's own signature. Chose the narrower signature. Why: the function is pure domain logic with no business needing anything from `ctx` beyond the database handle and the acting user's id — accepting the whole context would let it silently start depending on `ctx.token` or other fields later without that dependency being visible at the call site, and it makes the function trivially callable from a plain script or a future non-tRPC caller without constructing a fake context object.

**Fixing `admin.classUtilisation`'s correlated-subquery bug (`known-issues.md` #9), rather than documenting it like the other eight.** Alternative: document-only, consistent with every other pre-existing bug found this session. Chose to fix it, in its own commit, sequenced after a characterization test pins the current wrong values and after the `known-issues.md` entry lands. Why: every other documented bug involves a genuinely ambiguous "correct" behavior — a product decision this refactor has no authority to make (should an unfunded promotion fail, or go through at negative credits?). This one has no such ambiguity: the source code's own `sql` template says `${bookings.classId} = ${classes.id}`, a plainly-stated intent that a framework rendering quirk silently discarded at the SQL level. There is no competing interpretation of "correct" to weigh — restoring the written intent invents no new rule. It's also a data-correctness defect in a report someone could act on, not a policy edge case. The tension with "same outputs" is real and is stated explicitly in the `known-issues.md` entry rather than argued around — this is a deliberate, disclosed, single exception, not a reinterpretation of the rule.

**Verification method for the fix candidate: `.toSQL()` plus a real-data comparison script, not just re-reading the source more carefully.** Alternative: trust the finding because the reasoning in the source document was internally consistent and plausible. Chose to independently reproduce it — generated the actual SQL Drizzle emits for both the buggy shape and the safe (`classes.list`) shape via `.toSQL()`, then ran both the buggy query and a manually-correlated equivalent against the real seeded database side by side. Why: a plausible-sounding claim about framework behavior is still a claim; the working brief's whole methodology is "verify before acting," and this specific finding was handed over with an explicit instruction to do exactly that. The independent verification also caught something the source document got wrong: it claimed "exactly two raw correlated subqueries" exist repo-wide; a full grep-based audit found seven, five of them in `reschedules.ts`'s `history` query, previously unaudited by that document. All five turned out to be safe (their outer query already joins `classes`, so nothing renders unqualified), but that conclusion required checking, not assuming — the safety was in the same class of claim as the bug itself, and asserting a table has been fully audited is exactly the kind of statement this project's methodology says to re-verify rather than restate.

**Chose `leftJoin` + `groupBy` over `sql.raw` for the bug #9 fix, despite `sql.raw` being a smaller diff and also verified correct.** Alternative: `sql.raw('"classes"."id"')`, one line, tested and confirmed to produce correct values. Chose the larger rewrite instead. Why: a raw SQL string bypasses Drizzle's type system entirely — it isn't checked against the schema, doesn't get flagged if `classes` is renamed, and wouldn't show up in a "find references to this column" search. That's the exact same property that let the original bug ship silently: an intent written in source that nothing mechanical verifies against the database it's meant to describe. Fixing the bug with a technique that shares its root cause would mean the fix's own correctness rests on the same kind of unchecked assumption the bug itself was hiding behind — which reproduces the risk under a different name rather than retiring it. Also verified two things that could have quietly ridden along with this specific rewrite: row order (unspecified in both the original and the fix — confirmed empirically identical across four runs against seeded data, not merely "should be fine") and `LIMIT` semantics (confirmed it still limits distinct classes, not pre-aggregation join rows, by checking a class with 17 real bookings against `limit=5` and getting the correct count back rather than a truncated or inflated one).

**Added a characterization test for known-issues.md #10 specifically, not for #11-#14.** Alternative A: leave all five second-pass findings (#10-#14) as documentation-only, consistent with Tier 2 gating unused test coverage for `classes`/`plans`/`trainers`/`admin-companies` behind asking first. Alternative B: write tests for all five, for uniformity. Chose to test only #10. Why: bugs #1-9 each have a red/green test, but #10-#14 didn't, which is a real asymmetry a reviewer could flag — the newer findings are "asserted from reading source," a weaker form of evidence than the rest of the document uses. Closing that gap for all five would mean building out `classes`/`plans`/`trainers`/`admin-companies` test coverage wholesale, which is exactly the Tier 2 work the brief gates behind explicit permission — asked for, and granted, for #10 only. #10 alone gets the exception because it's the one flagged as most consequential (real credits/pool balances lost, not an edge-case timing bug), so it's the one worth the strongest form of proof; #11-#14 stay documentation-only. Verified the new `test/classes.test.ts` doesn't risk the existing 66 tests before writing it, not after: each test file provisions its own isolated temp SQLite db (`test/helpers/db.ts`), so there's no shared state a new file could disturb — confirmed empirically too, full suite green (70/70) after adding it.
